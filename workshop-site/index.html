Hands-on lab · ~75–90 minutes · O11y + optional ITSI

SecureBank Banking Platform Workshop

A 10-microservice React + Node.js banking demo with PostgreSQL, structured JSON logging, OpenTelemetry instrumentation, and admin-controlled feature flags — wired for Splunk Observability Cloud with an optional Splunk IT Service Intelligence (ITSI) integration module.

Who this lab is for

Splunk practitioners who want a realistic microservices demo: traces, RUM, logs, metrics, failure injection, and (optionally) how O11y alerts become ITSI episodes for service-centric incident response.

What you'll learn

How logs, traces, and metrics flow from microservices through the OTel Collector into Splunk O11y; how to demo the service map with business traffic; and how ITSI maps those signals to business services, KPIs, and episodes.

Live demo controls

Errors off

Toggle simulated database failures without leaving this page. After triggering, try a transfer in the app as Alice to see the 503 error and ERROR logs in Splunk (and optional ITSI notables).

Concepts 101 — Splunk O11y & ITSI

This lab uses Splunk Observability Cloud for application telemetry and optionally ITSI for service-centric correlation and business impact. Start here if you are new to the full stack.

Why ITSI on top of APM?

APM shows what broke in code and infrastructure. ITSI shows business impact: which customer-facing service is degraded, how KPIs roll up through dependencies, and how related alerts form an episode for faster MTTR. ITSI does not replace traces or logs — it correlates them at the service layer.

Frontend vs APM service map

The browser appears in RUM (securebank-frontend), not as an APM microservice node. Open a RUM session → View related trace to jump to backend APM via the Server-Timing header.

O11y UI filter guide — what to search in each view

SecureBank tags all backend telemetry with environment banking-app and namespace securebank. Set the environment filter first in every view — if you see no data, you are usually in the wrong environment (e.g. development) or the stack is not exporting yet.

Step 1~3 min

Prerequisites

  • Docker Desktop (or Docker Engine) for Compose path
  • Node.js 20+ and npm for seed, traffic, and flags scripts
  • Splunk Observability Cloud ingest token (Organization Settings → Access Tokens)
  • Splunk RUM public token in .env.splunk as SPLUNK_RUM_ACCESS_TOKEN
  • Minikube (optional) — 6 GB RAM recommended; npm run demo:up or npm run minikube:up
  • ITSI (optional, Step 9) — Splunk Enterprise or Cloud with ITSI licensed

Ports used: 5173 (app), 8080 (API), 8090 (workshop), 8025 (mail), 4317/4318 (OTel).

Step 4~5 min

Structured logging for Splunk

Every service emits single-line JSON logs with Splunk-compatible severity fields:

{
  "timestamp": "2026-06-18T12:00:00.000Z",
  "severityText": "INFO",
  "severityNumber": 9,
  "body": "GET /accounts/ 200",
  "service.name": "account-service",
  "deployment.environment": "banking-app",
  "correlation_id": "uuid-here",
  "trace_id": "abc123...",
  "span_id": "def456...",
  "http_method": "GET",
  "http_route": "/",
  "http_status": 200,
  "duration_ms": 12
}
Docker logs
docker compose logs -f transaction-service | jq .
docker compose logs -f transaction-service | jq 'select(.severityText == "ERROR")'

# Minikube
kubectl -n banking logs deploy/transaction-service --since=5m | jq .
In Log Observer: deployment.environment:banking-app severityText:ERROR or service.name:transaction-service

Admin-controlled flags simulate database insert failures for observability and ITSI episode demos.

When enabled, the API returns HTTP 503 with code: FEATURE_FLAG_BLOCKED and logs an ERROR with feature_flag in the JSON payload — ideal for O11y detectors and ITSI notables.

Step 8~10 min

ITSI concepts — SecureBank mapping

ITSI sits on Splunk Platform and correlates signals from O11y (and other sources) into service health and episodes.

End-to-end flow

SecureBank app
transfers, flags
OTLP
Splunk O11y
traces · metrics · logs
detector
Webhook → HEC
Splunk Platform
ingest
ITSI
notables · episodes · KPIs

SecureBank ITSI model (recommended)

ITSI objectSecureBank mapping
Business serviceSecureBank Digital Banking (parent) with child Funds Transfer
Entitiesapi-gateway, transaction-service, account-service (from APM)
KPIsTransfer error rate, p90 latency, availability (from O11y metrics)
Notable eventsO11y detector fires on 503 / error rate → HEC payload
EpisodesCorrelated notables when feature flag causes cascading failures

O11y vs ITSI — complementary roles

  • O11y — deep dive: span-level debugging, RUM sessions, service map, detectors
  • ITSI — service lens: health scores, dependency impact, episode management, glass table
  • Use O11y to find the broken span; use ITSI to communicate business impact and coordinate response

Official docs: ITSI services · Episodes · O11y detectors

Step 9~20 min · optional

ITSI optional hands-on lab

Requires ITSI

Skip this step if ITSI is not available. Facilitators can walk through concepts (Step 8) and show the O11y failure demo instead. See WORKSHOP_GUIDE.md for talking points.

1. Create an O11y-linked ITSI service

  1. ITSI → Configuration → Services → Create New Service
  2. Title: SecureBank Funds Transfer
  3. Template: Splunk APM Business Workflow KPIs (or link entities manually)
  4. Entity search: service.name:transaction-service with deployment.environment:banking-app
  5. Enable service and backfill KPIs (7 days default)

2. Create an O11y detector

  1. O11y → Detectors & SLOs → New Detector
  2. Signal: error count or 503 rate on transaction-service
  3. Filter: deployment.environment:banking-app
  4. Threshold: alert when errors exceed baseline during demo

3. Wire detector → ITSI (HEC webhook)

  1. Splunk Platform → Settings → Data Inputs → HTTP Event Collector → New token (e.g. o11y_alerts_for_itsi)
  2. O11y → Data Management → Integrations → Splunk platform → add HEC URL + token
  3. Edit detector → Alert Recipients → Splunk platform → select integration for Critical/Warning

4. Demo correlation

  1. Ensure baseline traffic: npm run traffic
  2. Click Trigger errors on this page (fail_transaction_insert)
  3. Attempt transfers — 503 errors flow to O11y
  4. Detector fires → notable event in ITSI
  5. ITSI → Episode Review or Service Analyzer — see degraded Funds Transfer health
  6. Click Turn off errors — KPIs recover after cache TTL (~60s)
Validate in Splunk Platform (index varies by org)
index=itsi_event_management OR index=main sourcetype=o11y:itsi:alert
| search service.name=transaction-service OR title=*transfer*

Troubleshooting

Nothing in Splunk APM or service map

Look in APM → Services, not Infrastructure. Filter environment banking-app.

docker inspect banking-platform-otel-collector-1 --format '{{range .Config.Env}}{{println .}}{{end}}' | grep SPLUNK_ACCESS_TOKEN
npm run traffic
kubectl -n banking logs deploy/otel-collector --since=5m | grep -i trace

Admin-only traffic centers the map on admin-service. Use transfers for business topology.

No logs in Log Observer (404 on export)

Log Observer does not use a Platform index. Use ingest token; try SPLUNK_LOG_INGEST_URL in .env.splunk.

kubectl -n banking logs deploy/otel-collector --since=5m | grep -iE 'LogsExporter|404'
RUM sessions not appearing

Set SPLUNK_RUM_ACCESS_TOKEN in .env.splunk and restart frontend. Verify VITE_DEPLOYMENT_ENVIRONMENT=banking-app.

ITSI notables not arriving

Verify HEC token, index permissions, and Splunk platform integration in O11y. Test with a manual detector fire. Index name varies — ask your Splunk admin.

Feature flag has no effect

Flags cache for 60 seconds. Wait after toggling. Verify admin-service is running.

Port-forward / connection refused

Run npm run minikube:port-forward in the same session as npm run traffic.
